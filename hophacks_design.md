# AidGraph

**An actionable resource planner for people seeking community support.**

HopHacks 2026 — Design Document

---

## 1. One-Line Pitch

AidGraph turns a person's situation into a verified, step-by-step plan for reaching the community resources they need.

Rather than returning a list of shelters, food banks, transportation services, or assistance programs, AidGraph connects those resources together and computes an actionable path based on the person's real constraints.

## 2. Problem

People seeking community assistance usually face several problems at once. A typical situation:

> "I lost my housing today. I don't have a car, I only have $10, and I need somewhere to stay tonight."

A conventional search returns a directory: ten or more shelters, food pantries, government websites, nonprofit listings, PDFs describing eligibility rules, and a scattering of phone numbers and addresses.

The information technically exists, but the person is still left to work out:

- Which resources apply to them?
- Which ones are open right now?
- Are they eligible?
- What documents do they need to bring?
- Can they physically get there?
- What has to happen first?
- What happens if one of those resources turns out to be unavailable?

The core problem is not finding resources. It is figuring out how to use them together.

## 3. Solution

AidGraph models local community resources as a structured graph. Each resource records:

- Service provided
- Location
- Hours of operation
- Eligibility requirements
- Required documents
- Cost
- Transportation constraints
- Availability or capacity, where known

The person describes their situation in plain language. AidGraph then:

1. Identifies the person's needs and constraints.
2. Finds relevant, verified resources.
3. Builds dependencies between those resources.
4. Determines a feasible sequence of actions.
5. Produces a step-by-step plan.
6. Replans automatically if a resource becomes unavailable.

Instead of "Here are 15 shelters near you," AidGraph produces:

```
6:10 PM   Call Shelter A
          4 beds available. Photo ID required.

6:25 PM   Take CityLink Red
          Estimated travel time: 22 minutes.

7:00 PM   Check in at Shelter A

Tomorrow, 9:00 AM   Visit Resource Center B
          Begin longer-term housing assistance application.
```

## 4. Example User Flow

**Input**

> "I'm 19, I have nowhere to stay tonight, I don't have a car, and I only have $10."

**Step 1 — Need extraction**

Identified needs:

- Emergency housing
- Food
- Transportation
- Longer-term housing assistance

Identified constraints:

- No car
- $10 budget
- Needs housing tonight
- Age: 19

**Step 2 — Resource graph**

```
                Emergency Housing
                        |
           +------------+-------------+
           |                          |
       Shelter A                  Shelter B
           |                          |
      Requires ID              No ID required
           |
     Transportation
           |
       Bus Route X
           |
          Food
           |
       Pantry C
```

**Step 3 — Planning**

AidGraph selects a feasible path by evaluating eligibility, hours, distance, transportation, dependencies, availability, and the person's constraints.

**Step 4 — Action plan**

The person receives a chronological plan rather than a resource directory.

**Step 5 — Dynamic replanning**

Suppose Shelter A becomes unavailable:

```
Shelter A   AVAILABLE → FULL
```

AidGraph invalidates the affected path and searches the graph again.

```
Old plan:  Shelter A → Bus Route X → Pantry C
                        ↓
New plan:  Shelter B → Bus Route Y → Community Kitchen D
```

This is one of the primary demo moments.

## 5. Key Features

### A. Natural-language situation input

People describe their situation in their own words instead of completing a complex form.

> "My friend needs somewhere to stay tonight, doesn't have a car, and hasn't eaten today."

An LLM converts this into structured needs and constraints.

### B. Verified resource database

Resources are stored in a structured format rather than being generated by an LLM. Example:

```json
{
  "name": "Example Emergency Shelter",
  "service": "emergency_housing",
  "hours": { "open": "18:00", "close": "08:00" },
  "requires_id": true,
  "minimum_age": 18,
  "cost": 0,
  "location": "...",
  "capacity": 4
}
```

This prevents the model from inventing requirements, hours, or services.

### C. Resource graph

Resources are represented as connected nodes rather than independent search results.

Node types may include needs, services, organizations, requirements, documents, and transportation options.

Edge types may include `requires`, `provides`, `located_near`, `reachable_by`, `eligible_for`, and `depends_on`.

### D. Constraint-aware planner

The planner determines whether a resource is actually usable for this person.

```
Person:     No car · Budget ≤ $10 · Needs shelter before 9:00 PM
Shelter A:  Intake closes 8:00 PM · Requires ID
Bus:        Arrival 7:42 PM
```

This path is valid. If the arrival time shifts to 8:15 PM, the path must no longer be recommended.

### E. Map view

The final plan is visualized geographically. The map shows the person's location, the shelter, food resources, transportation, and other assistance, with the selected route highlighted so the person sees both what to do and where to go.

### F. Live replanning

A resource can be marked **Full**, **Closed**, **Unavailable**, or **Delayed**. AidGraph automatically computes an alternative plan. This is what makes the product feel like a planner rather than a static search engine.

## 6. System Architecture

```
            User situation
                  |
                  v
         LLM need extraction
                  |
                  v
      Structured user constraints
                  |
                  v
          Resource database
                  |
                  v
           Resource graph
                  |
                  v
    Constraint / planning engine
                  |
         +--------+--------+
         |                 |
         v                 v
     Route / map      Explanation
         |                 |
         +--------+--------+
                  |
                  v
          Actionable plan
```

**Role of the LLM**

- Understanding natural-language requests
- Extracting needs and constraints
- Explaining the generated plan

**Role of deterministic logic**

- Eligibility checks
- Opening hours
- Dependency validation
- Resource availability
- Route feasibility
- Plan construction

**Guiding principle:** the LLM understands the situation; the planner determines what is actually possible.

## 7. Proposed Tech Stack

| Layer | Choice |
|---|---|
| Frontend | Next.js / React, Tailwind CSS, Mapbox or Google Maps |
| Backend | Python, FastAPI |
| Data | PostgreSQL / Supabase, or a small curated Baltimore dataset for the hackathon |
| Graph / planning | NetworkX, custom graph search, Dijkstra/A*, constraint filtering before traversal |
| AI | Gemini / OpenAI / Claude API with structured JSON output for need extraction |

A full graph database is not required for the MVP.

## 8. Hackathon MVP

The project is intentionally kept small.

**Geographic scope:** Baltimore only.

**Supported needs:** emergency housing, food, and transportation, with longer-term assistance as an optional fourth.

**Dataset:** approximately 20–30 curated resources. The goal is not comprehensive coverage; it is demonstrating that the planning system works.

**Required MVP features**

- Natural-language situation input
- Need and constraint extraction
- Resource database
- Resource graph
- Feasible plan generation
- Step-by-step timeline
- Map visualization
- Resource availability toggle
- Automatic replanning

## 9. Stretch Goals

Attempt these only after the core demo works.

- **Multilingual support.** A person asks for help in Spanish, Korean, or another language while the underlying resource data stays structured.
- **Document assistance.** When a service requires, for example, proof of income and a photo ID, AidGraph explains exactly which documents to prepare.
- **Accessibility.** Voice input and output for people who have difficulty navigating complex websites.
- **Organization dashboard.** Nonprofits update capacity, status, and food availability, and the change immediately affects future plans.
- **Multiple people and families.** Account for family size, children, accessibility needs, and pets.

## 10. Demo Scenario

**Opening**

> "When someone is in crisis, finding a resource isn't enough. They need to know what to do next."

**Input**

> "I'm 19. I lost my housing today, don't have a car, have $10, and need somewhere to sleep tonight."

**Sequence**

1. AidGraph extracts the situation.

   ```
   Housing          HIGH PRIORITY
   Food             HIGH PRIORITY
   Transportation   REQUIRED
   Budget           $10
   Vehicle          None
   ```

2. The resource graph appears, showing relevant resources and their dependencies.

3. AidGraph generates an actionable plan.

   ```
   6:15 PM    Take Bus X
   6:42 PM    Pick up dinner at Resource B
   7:05 PM    Arrive at Shelter A
   Tomorrow   Visit Resource C for longer-term housing assistance
   ```

4. The map shows the entire plan as a route.

5. The demo moment: change Shelter A from **Available** to **Full**.

6. AidGraph replans. The previous route disappears and a new feasible plan is generated.

**Closing line**

> "Resource directories tell people what help exists. AidGraph tells them how to actually reach it."

## 11. Why This Is Different

AidGraph is not another resource-search chatbot. A chatbot can retrieve "here are five nearby shelters." AidGraph asks a different question:

> Given this person's constraints, what sequence of resources can actually solve their problem?

The technical differentiation comes from combining natural-language understanding, structured verified data, graph representation, constraint reasoning, route planning, and dynamic replanning. The result is an action plan, not an answer.

## 12. Risks and Cautions

**Data accuracy.** We do not claim information is real-time unless we have a real-time source. For the hackathon, availability changes are clearly presented as simulated nonprofit-side updates.

**High-stakes decisions.** AidGraph does not independently determine whether someone legally qualifies for a benefit, nor does it guarantee that a service will accept them. It presents source information, known requirements, contact details, and recommended next steps.

**Scope creep.** We are not building a national platform during the hackathon. A polished Baltimore demo with 20–30 resources is far better than an incomplete system covering hundreds of organizations.

## 13. Goals for HopHacks

The strongest version of AidGraph demonstrates three things:

- **Impact.** Someone facing a complicated situation receives a clear path to assistance.
- **Technical depth.** The system reasons over constraints and dependencies instead of simply generating text.
- **Demo quality.** A judge can immediately see the plan, the map, and live replanning happen.

**Core concept:** search finds resources. AidGraph connects them into a plan.

## Appendix: Hackathon Execution Plan

### MVP goal

Complete the following flow within 36 hours:

```
Situation input → need/constraint extraction → filtering of feasible local resources
→ plan generation → timeline and map display → automatic replanning on status change
```

### Scope

Baltimore only. Three resource types initially: emergency housing, food, and transportation. Roughly 20–30 hand-curated resources.

### Tech stack

- Frontend: Next.js + Tailwind
- Backend: FastAPI
- Data: JSON or Supabase
- Planner: Python + NetworkX
- AI: LLM API
- Map: Mapbox or Google Maps

### Core capabilities

**Natural-language input.** "I'm 19, have no car, only $10, and need somewhere to stay tonight" becomes structured needs (housing, food, transportation) and constraints (age 19, $10 budget, no car, deadline tonight).

**Resource filtering.** Remove resources that fail on age limits, ID requirements, hours, cost, current availability, or reachability.

**Planner.** From the remaining resources, choose the most feasible route, for example Community Kitchen → Bus → Emergency Shelter, scored simply on distance, time, and cost.

**Timeline and map.** Present the result as an ordered sequence of actions (6:20 PM pick up dinner, 6:45 PM take bus, 7:10 PM check in at shelter) and show the same route on the map.

**Dynamic replanning.** When Shelter A changes from Available to Full, discard the existing plan and generate a new one using a different shelter. This is the main demo moment.

### Development order

| Phase | Work |
|---|---|
| Early | Repository and frontend/backend setup, resource schema, sample resource data, planner first |
| Middle | LLM input parsing, frontend timeline, map integration |
| Late | Resource status changes, replanning, UI polish, demo stabilization |

### Team roles (four people)

| Role | Responsibility |
|---|---|
| Backend / Planner | Filtering, graph, planning, replanning |
| Data / AI | Baltimore resource data, LLM parsing |
| Frontend | Input, timeline, resource UI |
| Map / Integration | Map, routing, end-to-end integration and polish |

### Must-ship features

1. Natural-language input
2. Constraint extraction
3. Resource filtering
4. Plan generation
5. Timeline
6. Handling of unavailable resources
7. Automatic replanning

Map and multilingual support are deprioritized if time runs short.

### Guiding principle

The LLM never decides the answer directly.

- LLM = understands the person's situation
- Planner = computes what is actually possible

AidGraph's purpose is not simply to find resources, but to turn a person's situation into a concrete, executable next action.
